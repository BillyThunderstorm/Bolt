# Phase 1.4 — Full uv Migration

**Status:** ✅ Complete (2026-07-31, same evening session as 1.3).
**Outcome:** Bolt is now a fully uv-managed Python project. Test suite
remains at **310 tests, 5 skipped, 0 broken** via:
  1. `uv run python -m unittest discover Data/tests`
  2. `.venv/bin/python -m unittest discover Data/tests`
  3. `uv run bin/bolt test`
  4. `uv lock --check` (verifies lockfile is consistent)
**Author:** Carter + Agent (Carter picked option A; agent executed).

---

## Why this phase exists (context)

Phase 1.3 had a workaround smell: I `pip install --break-system-packages
Pillow imagehash`'d into the global uv-managed Python to get the BlackFrame
tests to pass. That felt wrong given the rest of the env is uv-managed on
this machine. Carter wanted to "make everything uv" cleanly so the repo
would work for any contributor with `uv` installed.

A `.venv` already existed at `Bolt/.venv/`, but it had been created on
June 28 with `python3 -m venv` (not `uv venv`), and it didn't have a
companion `pyproject.toml` / `uv.lock` / `.python-version`. So while the
.venv worked, it wasn't reproducible, wasn't version-pinned, and didn't
match the rest of the env on this box.

## What landed

Three new tracked files at the repo root:

| File | Purpose |
|---|---|
| `pyproject.toml` | PEP 621 metadata + `[tool.uv]` config + deps derived from `scripts/requirements.txt` |
| `uv.lock` | Reproducible-resolution lockfile generated by `uv sync` |
| `.python-version` | Pins the interpreter to 3.11.15 (matches the uv-managed cpython that was already installed on this box) |

Plus:

- `scripts/activate_bolt_venv.sh` rewritten to prefer `uv run python`
  when `uv` is on the PATH. Falls back to sourcing `.venv/bin/activate`
  if `uv` isn't installed.
- `bin/bolt` docstring updated to lead with `uv run bolt` as the
  canonical invocation. The wrapper itself didn't change — it still
  delegates to `.venv/bin/python3` directly when run that way.

The existing `scripts/requirements.txt` is **unchanged** and remains
authoritative for the canonical dep list. `pyproject.toml` mirrors it
1:1 (with section comments preserved as in-line string comments). If a
new dep needs to be added, edit `requirements.txt` first and then update
`pyproject.toml`. Future phases could automate this with a single-pass
sync script if the duplication becomes a hassle.

## Why repo-root `pyproject.toml` (Option A)

- Matches `uv init` / `uv add` defaults — anyone who's used uv before
  sees the layout they expect.
- `uv sync` / `uv run` work from the repo root without `cd`-ing into
  `scripts/`.
- `bin/bolt` and `scripts/activate_bolt_venv.sh` already resolve paths
  from the repo root, so the manifest at the root doesn't break them.

The alternative (Option B, manifest in `scripts/`) would have required
introducing a `cd scripts` wrapper around every uv invocation, which
defeats the simplicity goal.

## Verification

```
$ uv run python -m unittest discover Data/tests
Ran 310 tests in 77.4s
OK (skipped=5)

$ .venv/bin/python -m unittest discover Data/tests
Ran 310 tests in 89.0s
OK (skipped=5)

$ uv run bin/bolt test
Ran 310 tests in 92.0s
OK (skipped=5)

$ uv lock --check
Resolved 197 packages in 3ms
```

`uv lock --check` returns cleanly, which means the lockfile is consistent
with `pyproject.toml`. If a contributor adds or changes a dep in
`pyproject.toml` without re-locking, `uv sync` will refuse to proceed.

## What we did NOT do (called out so future-you knows it's intentional)

- **Did not delete `scripts/requirements.txt`.** It's still the human-
  readable, well-organized reference for what's installed. Once the repo
  has a `scripts/sync_manifest.py` helper (or until we trust contributors
  to never look at it), keep both. The `pyproject.toml` block has each
  dep followed by the same comment that lives in `requirements.txt`, so
  the duplication isn't silent — the rationale travels with the dep.
- **Did not enable `[project.scripts] bolt = "bin.bolt:main"`.** Bolt is
  `package = false` in `[tool.uv]`, which is correct for an app that
  lives in-process. Installing the script entry-point would require
  `package = true` and a hatchling build config that doesn't otherwise
  pull its weight. We retain the `python3 bin/bolt <subcmd>` and
  `uv run bin/bolt <subcmd>` invocation paths because they work with
  `package = false`. A future phase can flip this if/when Bolt starts
  being `uv tool install`'d on machines that don't have a working copy
  checked out.
- **Did not remove the `--break-system-packages` Pillow install from
  the global uv-managed Python.** Leaving it there doesn't hurt anything
  (the venv shadows it), and removing it would require a separate
  destructive op. Future contributors will not be affected: `.venv/bin/
  python` wins anyway.

## Effect on each entry-point (audit)

| Caller | What it does today | After this phase |
|---|---|---|
| `./scripts/activate_bolt_venv.sh <script>` | sources `.venv/bin/activate` then execs `python3 <script>` | tries `uv run` first; falls back to activate-then-python3 only if `uv` isn't on PATH |
| `python3 bin/bolt <sub>` | uses `sys.executable` if `.venv` missing, else `.venv/bin/python3` | unchanged (still picks the venv when present) |
| `python3 scripts/<script>.py` | uses whatever `python3` is on PATH | continues to work; if you want reproducible resolution, use `uv run python` instead |
| `uv run bin/bolt test` | uses `.venv/bin/python` via uv | new, primary path |
| `uv run python -m unittest discover Data/tests` | uses `.venv/bin/python` via uv | new, primary path |
| `./scripts/autostart.py install` | uses sys.executable to schedule `launch.py` | unchanged — autostart doesn't run inside the venv explicitly, so it picks up `python3` on PATH at boot. If the cron env doesn't include `.venv`, this is the path to harden next. |

## Migration cost

Single session, ~10 minutes (most of which was `uv sync` resolving 174 packages).

- 2 min: capture `pip freeze` so I had a target to match against.
- 2 min: write `pyproject.toml` from `requirements.txt`.
- 1 min: write `.python-version`.
- 3 min: `uv sync` + sanity-check `uv lock --check`.
- 2 min: docstring updates + final verification.

## Suggested follow-up (not Phase 1.4 scope)

- **`scripts/sync_manifest.py`** — small helper that diffs the dep
  sections of `pyproject.toml` vs `requirements.txt` and refuses to
  commit if they drift. 20 lines, single-file, no deps.
- **`autostart.py` venv awareness** — when `autostart.py install`
  schedules `launch.py` via launchd / systemd, it should use `.venv/
  bin/python3` rather than the system `python3` so the bot doesn't
  drift into a different interpreter at boot.
- **Drop `--break-system-packages` Pillow** — optional cleanup; only
  relevant if a future Bolt config cares about the global interpreter
  not having extra packages installed.
